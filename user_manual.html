What is GIS Co-Scientist?

GIS Co-Scientist is a multi-agent framework for autonomous geospatial scientific inquiry, retrieving geospatial data, running spatial analyses, and producing full research manuscripts through a single conversational interface.

There are two ways to use it:

  • Desktop app (recommended) - for Windows and macOS. See Installing the Desktop App.
  • WebUI - runs in your browser, with nothing to install. See Using the WebUI.

GIS Co-Scientist has four working modes that you switch between depending on the type of task you want the system to run:

Data Retriever

Find and download geospatial datasets from built-in public sources.

Spatial Analysis

Run a specific spatial analysis on your data.

Research

The full pipeline: research plan generation, spatial modeling, interpretation, and manuscript writing.

Chat

Conversational Q&A

Installing the Desktop App

The desktop app is the recommended way to use GIS Co-Scientist. It runs on Windows and macOS in its own window, and your conversations, uploads and outputs stay on your computer.

Windows

Requires 64-bit Windows 10 or 11 and about 900 MB of free disk space. No administrator rights are needed.

1
Download GIS-CoScientist-Setup-<version>.exe from the Windows download page.
2
Double-click the file. If Windows shows "Windows protected your PC", click More info, then Run anyway.
3
Follow the installer. Tick Create a desktop shortcut if you want one. The app installs to %LOCALAPPDATA%\Programs\GIS Co-Scientist and is added to the Start menu. The installer also checks for the Microsoft Edge WebView2 runtime, which the app needs (it is already part of most Windows 10 and 11 computers).
4
Open GIS Co-Scientist from the Start menu or the desktop shortcut, then add your OpenAI API key in Settings (see API Key).

macOS

There are two builds: arm64 for Apple Silicon (M1 and later) and x86_64 for Intel Macs. To check which Mac you have, open the Apple menu → About This Mac.

1
Download GIS-CoScientist-<version>-<arch>.dmg for your Mac from the Apple Silicon or Intel download page.
2
Open the .dmg and drag GIS Co-Scientist into Applications.
3
The first time you open it, macOS may say "GIS Co-Scientist" Not Opened because Apple could not verify it. To allow it (you only need to do this once):
  • macOS 15 Sequoia and later: click Done on the message, open System Settings → Privacy & Security, scroll down to Security, and click Open Anyway next to GIS Co-Scientist. Enter your password, then click Open Anyway again.
  • macOS 14 Sonoma and earlier: right-click (or Control-click) the app in Applications, choose Open, then click Open again.
After that it opens normally.
4
Open the app, then add your OpenAI API key in Settings (see API Key).

Updating and uninstalling

  • Update: install the newer version over the old one (on macOS, replace the app in Applications). Your conversations, uploads and outputs are kept.
  • Uninstall (Windows): Settings → Apps → Installed apps → GIS Co-Scientist → Uninstall. Your conversations, uploads and outputs are left in the install folder; delete %LOCALAPPDATA%\Programs\GIS Co-Scientist to remove them too.
  • Uninstall (macOS): drag the app from Applications to the Trash. Your data is in ~/Library/Application Support/GIS Co-Scientist; delete that folder to remove it too.

Quick Start

Open the desktop app (recommended) or the WebUI, then follow these steps.

1
Add your API key: Click Settings (top-right), paste your own OpenAI API key (sk-) into the API Key field, and click Save Key. See API Key for how to get one, or for the backup option if you only want to try the system.
2
Pick a mode: In the chat input toolbar, open the mode dropdown (bottom-right of the input box) and choose Data Retrieval, Spatial Analysis, Research, or Chat.
3
Upload data (Optional): Click the ＋ button (or the button in Data Layers, top of the right panel) to load your own shapefile, GeoPackage, GeoJSON, CSV, or raster. If you don't have data, the Data Retriever can fetch it.
4
Set Auto Data (Optional): Use the Auto Data switch in the mode dropdown (on by default) to control how datasets are fetched. NOTE:  Turn on Autonomous mode (in the mode dropdown) if you want the system to auto-approve its own plans and run end-to-end with minimal interruption (see Choosing a Mode).

UI Layout Overview

Left sidebar

  • Top row: New chat starts a fresh conversation (see Conversation History and Sharing), and the ◧ button collapses the sidebar.
  • Conversations: your saved conversations under Recent, with filter and sort controls.
  • Data Sources: a second tab listing the data sources the assistant can retrieve from (see Adding a New Data Source).

Center (Chat area)

The middle panel is the conversation itself: the assistant's messages and a multi-line input box at the bottom. Below the input box is a toolbar:

  • ＋ Add data - upload a dataset (same as the button in Data Layers).
  • Mode selector - choose the working mode, and switch Autonomous and Auto Data on or off (see Choosing a Mode).
  • Model selector - shows the model. Changing it does not change the model that runs (see LLM Models used).
  • Send - submit your request (also doubles as a Stop button while running).

Each stage of a run appears in the chat as a card. Its Tokens chip shows how many tokens the stage's language-model calls have used so far, and it keeps counting through re-runs, revisions, result analysis and manuscript drafting. Click the chip to see the stage's input, output and total tokens, the number of calls, and a per-call table naming the model used. The totals are saved with the conversation.

Right (layers, map and results)

The right region is stacked top to bottom. The ◨ button in the Data Layers header collapses the whole right panel.

  • Data Layers (top) - every dataset uploaded, downloaded, or produced in this conversation. The button adds a layer, and clicking the Data Layers title collapses or expands the list (see Data Layers).
  • Map Viewer (middle) - an interactive map that renders data layers.
  • Results and Artifacts (bottom) - analysis outputs, tables, figures, statistics, and report downloads. Clear it with the × button. Drag the divider between the map and this panel to resize them.

Result layers and reloads

  • Results go to the map. When a Spatial Analysis run finishes, its vector outputs are added to Data Layers and drawn on the Map Viewer, and the run's main output opens in Results and Artifacts.
  • Layers survive a reload. A layer you add from your computer is saved to the conversation right away, and a Spatial Analysis run's map outputs are saved as conversation files. Reloading the page or reopening the conversation brings them back. A layer you remove stays removed, until you add it again, for example by clicking its download tile or using Add to Map on a result.
  • Follow-up requests can use result layers. Layers in the list, including results added with Add to Map, are sent with your next message. For example, after a run that creates county centroids you can ask for "100 m buffers around the centroids" and the system reuses that layer instead of computing it again.

Conversation History and Sharing

Conversation History

  • Conversations are listed in the left sidebar, where you can filter, sort, and pin them. Open the ⋯ menu on a conversation to rename, export, or delete it.
  • Saved on your computer: conversations stay available if you replace your API key or switch between an OpenAI and a GIBD key. A key must be saved in Settings for the list to appear.
  • Not synced: entering the same key on another computer does not bring your conversations there. Use export and import instead.
  • Uploaded files and generated artifacts are stored with the conversation, so reopening it restores its state.
  • Deleting is permanent: the messages, uploaded data and outputs are removed from your computer. Export the conversation first if you may need it again.
  • In the WebUI: conversations are saved on the server against your API key, so entering the same key in another browser brings them back.
  • New chat starts a fresh conversation with its own data layers and workspace.

Autonomous mode

Inside the mode dropdown is an Autonomous toggle. When on, the system auto-approves its own plans and proceeds through checkpoints without pausing for human confirmation - useful for hands-off, end-to-end runs. When off (the default), it stops at each major checkpoint so human can review, revise, or approve.

When to use it:  Turn Autonomous on once you trust the request and want a complete result in one go; keep it off when you want to steer the analysis step by step.

LLM Models used

GIS Co-Scientist is a multi-agent system, so a single run is handled by more than one language model - each step makes its own model call. In the current release every one of those calls uses GPT-6 Luna. Each call's model and reasoning effort are set individually in the application's configuration, so a single step can be moved to a different model without affecting the rest.

ModeOperations / StagesModel
Data Retriever

  • Data source identification
  • Data download / query code generation

Spatial Analysis
  • User request interpretation
  • Geoprocessing workflow construction
  • Operation and analysis code generation, debugging

  • Question understanding
  • Data retrieval
  • Research plan generation and review
  • Code generation and debugging
  • Result analysis and interpretation

The reasoning effort is the model's default. Calls that use tools are sent with reasoning turned off, because GPT-6 Luna does not accept tools and reasoning together. Click a stage card's Tokens chip to see which model each of its calls used.

Geoprocessing Workflow

Before writing any code, GIS Co-Scientist constructs an explicit geoprocessing workflow. The geoprocessing workflow is represented as a directed graph where spatial input data → geoprocessing operations / tools → and output data are connected. Each analytical objective is decomposed into a sequence of spatial operations and the output of one step becomes the input for the next step. This geoprocessing workflow serves as an executable blueprint for any geospatial task.

Creating a data source handbook

A handbook is a complete data source definition which provides the technical information that GIS Co-Scientist needs to retrieve data from one specific source.

A handbook serves a single data source and is maintained on its own, so adding, updating, or removing a source is plug-and-play. It is normally saved in a structured file format (.toml).

Writing a good handbook

A handbook consists of three required parts: data_source_name, brief_description, and handbook.

FieldDescription
data_source_nameA short, meaningful, human-readable name - for example OpenStreetMap, US_Census_demography, US_Census_boundary, OpenTopography, OpenWeather, COVID_NYT, or ESRI_world_imagery.
brief_descriptionOne line describing the source so the assistant knows when to use it. Include the critical scope - geographic extent and time period. E.g. for COVID_NYT: "US COVID-19 data by the New York Times. Cumulative counts of COVID-19 cases and deaths in the United States, at the state and county level, from 2020-01-21 to 2023-03-23."
handbookThis is the most critical section of the handbook. This includes the technical requirements for downloading from the data source - one requirement per line. Cover the access URL and endpoints, the parameters and their allowed values, the column/attribute names.

Other fields of the handbook include: Code example, website

Optional fieldDescription
code_example A short, working Python snippet that downloads data from this source and saves it to a file. The assistant uses it as a verified template, so keep it self-contained: put the logic in a download_data() function with a final line that calls it, use {KEY_NAME} placeholders for any credentials, and save to a plain relative filename. See example
website The data source's official homepage. It's shown in the source's details for reference and lets users quickly verify or learn more about the provider.

Beyond these fields, a few best practices for the handbook (instructions):

  • Be explicit about endpoints and parameters. State the exact URL pattern, and for each parameter say what it means and what it accepts (allowed values, min/max, defaults).
  • Use placeholders for credentials. Write {KEY_NAME} wherever a key or login is needed - never hard-code a real key. (The placeholder names must match the credential names you list - see Sources that need an API key.)
  • Surface errors. Instruct the code to raise on failure (an invalid key, a bad response) rather than silently swallowing exceptions, so problems are visible.
Tip:  An example of a complete handbook is provided here: (Data source handbook example). In creating a new handbook, you don't have to start from scratch - download the example provided or other existing source as a .toml (the ⤓ icon), edit its handbook and code, and import it again.

Generating a handbook with Handbook Studio

Rather than writing a handbook by hand, you can have one generated and tested. Click Handbook Studio in the header to open it. It works through one source at a time, in three sections:

1
Setup - give the data source name, its documentation URL, or both, and optionally the retrieval task to test with. You can also choose the service type (REST API, STAC, OGC Service, ArcGIS FeatureServer, bulk or HTTP file download, SQL, or your own), or leave it on Auto-select. Pick the model used to generate the handbook, the model that writes and debugs the retrieval code, and the reasoning effort. The default is GPT-6 Luna at low effort for both.
2
Generate & retrieve - the model researches the source on the web, drafts the handbook and checks it, then pauses so you can review and edit it. Once you continue, it writes retrieval code from the handbook, runs it, and reports whether the run passed, failed, or produced the wrong output.
3
Session report - every run in the session, with exports.

The handbook review card has two buttons. One downloads the handbook as a .toml you can re-import later. The other adds it to My Sources as a private data source, and asks first if a source with the same name already exists. Sessions can be saved, shared by link, and duplicated from the Studio's header.

NOTE:  Handbook Studio works with your OpenAI API key, or with a GIBD key as a backup for trying it out. Its web research uses OpenAI web search, which a GIBD key reaches through the GIBD service.

Data Retrieval Mode

Data retrieval mode: Find and download geospatial datasets from public data sources, without running any analysis.

How to use it

1
Switch the mode to Data Retrieval.
2
Describe what you need in natural language. Be as specific as you can about the variables, geography, and time frame (See examples).
3
The system identifies the best matching data source, fetches the data, and adds it as a new data layer you can map and download.
The "Auto Data" toggle

The Auto Data switch, in the mode dropdown under Autonomous, controls whether data needed for a request is downloaded automatically. It is on by default. With it on, the system pulls required datasets without asking each time; with it off, it pauses for human confirmation before downloading. The switch appears only for Spatial Analysis and Research, the modes that may need extra data. Data Retrieval mode always downloads, so the switch is hidden there.

Downloading multiple datasets

You can ask for several datasets in one request (e.g. "download 2019 county boundaries and county-level obesity rates for California"). The system retrieves each one and adds them as separate data layers. Each is independently mappable and downloadable, and ready to be merged later in Spatial Analysis or Research mode.

Feedback and approval prompts

Data retrieval is interactive. Human may be asked to provide input at two points:

  • Source confirmation - if the system isn't fully sure which source to use, it asks you to use the proposed source, retry with a different one, or abort.
  • Download fallback - if a download fails or a needed file is missing, you can choose to proceed with available data, upload the missing file yourself, or abort the workflow. Uploaded files are audited automatically and folded into the run.
Best practice:  Be specific about year, geography level (county vs. tract), and variable name. Vague requests lead to more clarification prompts.

Spatial Analysis Mode

Spatial Analysis: Run a specific spatial analysis - the system plans the geoprocessing workflow, writes the code, and executes it.

How to use it

1
Switch the mode to Spatial Analysis.
2
Upload (or retrieve) the dataset(s) you want to analyze. The Auto Data mode can be on to automatically retrieve relevant data needed for the any spatial analysis.
3
State the analysis you want (See examples).
4
Review the task breakdown. It says what data the analysis needs and whether the data you already have is sufficient. If it is, nothing is downloaded, even with Auto Data on, and the chat says which requests were skipped.
5
Review the proposed geoprocessing workflow (the spatial input → operation → output graph described in Geoprocessing Workflow). Every dataset in the conversation is treated as a candidate. The workflow designer checks each one's area, time period, units and content against the question, and builds only the ones that fit into the graph. It lists every candidate as used or not used, with a reason. For example, a Pennsylvania county layer left over from an earlier request is left out of a California analysis. You can approve the workflow, or send feedback to revise it before anything runs.
6
The system generates the code, executes it, and returns maps, tables, statistics, and figures in the Results panel. Vector outputs are added to Data Layers and the Map Viewer automatically (see Result layers and reloads).

Reviewing and re-running

  • Inspect - every step shows the exact geoprocessing operation and the code that implements it.
  • Revise - give feedback in plain language and the workflow or code is regenerated.
  • Re-run steps - individual steps can be re-executed without restarting the whole analysis.
  • Build on the result - send a follow-up request in the same conversation. The result layers on the map are sent with it, so the next analysis can start from them.

Research Mode

Research: The complete pipeline - from research question to a drafted manuscript.

Research mode is the most comprehensive mode. Give it a research question and (optionally) data, and it works through the entire scientific process, pausing for human approval at each major checkpoint (unless Autonomous is on).

Starting a research run

  1. Select Research in the mode dropdown.
  2. Provide data in one of two ways: add your files as data layers, or turn on Auto Data in the mode dropdown so the system downloads what is missing. If you provide no data and Auto Data is off, the system asks you to do one or the other.
  3. Decide whether to turn on Autonomous. With it off (the default), the run stops at each checkpoint below. With it on, the run approves its own checkpoints and continues to the manuscript. It still stops if a data source needs an API key it does not have.
  4. Type your research question and send it.

The workflow stages

A research run passes through the stages below in order. Each stage appears in the chat as its own card with live progress.

1
Data audit - every data layer is opened and checked: its format, coordinate reference system, size, and columns. Files that open correctly are added to the run's data registry, the list of data that every later stage works from.
2
Question understanding and breakdown - the Research Question Understanding Agent reads your question with the data registry and produces a structured breakdown: a working title, the research intent, the question category, the spatial and temporal scale, the data required, whether the data you supplied is sufficient, and a list of data requests for anything missing. The run then stops at Checkpoint 1.
3
Data acquisition (only with Auto Data on, and only if data is missing) - the Geospatial Data Retrieval Agent handles each data request in turn. It chooses a source from its data-source handbooks (Checkpoint 2), writes and runs the download code, and shows the files it delivered. If no handbook fits the request, it can create one for a new source. Downloaded datasets are checked, added to the data registry, and shown in the Data Layers panel like your own uploads.
4
Research plan generation - the Planning Agent works in three passes:
  • Generate: it inspects the datasets with its tools and drafts the plan as objectives, each with a hypothesis and a sequence of analysis steps.
  • Review: a second pass checks the draft against the actual data (column names, join keys, and whether each step's inputs are produced by an earlier step) and corrects it.
  • Finalize: every step's inputs are linked to a dataset or to an earlier step's output, and every output is given a file location.
The plan is shown with its geoprocessing workflow, and the run stops at Checkpoint 3.
5
Code generation and execution - objectives run one after another. Within each objective:
  • Each step is assigned to the agent best suited to it (for example, the Data Agent for joins and cleaning, the Modeling Agent for statistical and spatial models).
  • The agent writes Python code for the step and runs it. Code, console output, and produced files appear in a tile for that step.
  • If the code fails, a debugger investigates the error (checking columns, file paths, coordinate systems, and earlier outputs), repairs the code, and runs it again, up to two repair attempts per step.
  • If a step still fails or produces empty data, any later step that depends on its output is skipped rather than run on missing input. You can fix and re-run these steps at Checkpoint 4.
Progress is saved after every step, so a reload does not lose completed work.
6
Result analysis - the Result Analysis Agent collects the outputs of every step, by objective, and builds a figures and tables catalog: the maps, charts, and result tables that will go into the paper, each with a caption. The catalog is shown as thumbnails in the chat.
7
Manuscript drafting - the Reporting Agent searches the literature (Semantic Scholar) for papers related to your question and objectives, then writes the paper one section at a time, in order: Title & Abstract, Introduction, Methodology, Results, Discussion, Conclusion, and References. Each section appears in the chat as soon as it is written. See The manuscript deliverable.
8
Execution flowchart - finally, a flowchart of the steps that actually ran is generated. Click any step in it to see that step's code and outputs.

Human-AI collaboration in the research mode

GIS Co-Scientist incorporates human-in-the-loop checkpoints at the stages where expert judgment most strongly conditions the validity of downstream inference. At each checkpoint you can either approve and let the system proceed, or provide feedback that re-prompts the responsible agent with targeted revisions - all before any external code is generated or executed.

CheckpointWhen it appearsWith Autonomous on
1 - Task breakdownAfter question understandingProceeds automatically
2 - Data source selectionFor each data request, with Auto Data onProceeds automatically, but still stops for a missing or rejected API key
3 - Research plan reviewAfter plan generationPlan is approved automatically
4 - Execution reviewAfter all objectives have runSkipped
Checkpoint 1 - Task breakdown and data requirements

The first checkpoint follows the research question understanding stage, where the breakdown and the data requirements are shown, along with whether the data you supplied is sufficient. Two options are given:

  • Proceed - instructs the system to move on to retrieval and planning.
  • Provide feedback - you can give feedback in natural language describing what's missing or wrong. Only the parts your feedback asks about are revised, and you can review again.

If data is missing and Auto Data is off, the card offers to turn Auto Data on for this run, or to continue with only the data you have. If the breakdown judges your data sufficient, nothing is downloaded, even with Auto Data on, and the chat notes which requests were skipped.

Checkpoint 2 - Data source selection (optional)

A second checkpoint is triggered by the Geospatial Data Retrieval Agent once it has selected an appropriate data source for each unmet data requirement. The chosen source is shown with the rationale for its selection and a confidence score. Before any download code is generated, you can:

  • Proceed with the suggested source, or Always Proceed to accept the agent's choice for the remaining requests in this run.
  • Change the source to another one from the list, or generate a new skill (handbook) for a source the system does not know yet.
  • Enter an API key if the source needs one. Keys you enter are reused for later requests to the same source. See also Sources that need an API key.
  • Retry or abort the request.

After the download, you can review the files that were delivered before the run continues. If a request fails, you can retry it, skip it and continue with the data you have, or stop the run.

Checkpoint 3 - Research plan review

The third checkpoint occurs during research plan generation. Through a dedicated revision interface you can operate on the finalized plan before approving it for execution.

The planner treats every dataset in the conversation as a candidate. It checks each one's area, time period, units and content against the question, and plans only with the datasets that fit. Where nothing fits, it flags a data gap rather than stretching an unfit dataset. It records every candidate as used or not used, with a reason, and the plan reviewer checks this data fitness first. In the plan review you can:

  • Edit the plan directly - change an objective's title or hypothesis, edit step descriptions, and add or delete steps. When you delete a step, the system re-links the remaining steps so that none of them depends on the deleted step's output. The geoprocessing workflow is redrawn to match.
  • Provide feedback - give natural-language feedback describing the desired changes to the plan, and the system regenerates a revised plan based on your input.
  • Approve Plan - starts code generation and execution.
Checkpoint 4 - Execution review

The fourth checkpoint occurs immediately after objective execution. An execution checkpoint surfaces a per-step summary of statuses (completed, error, or skipped), errors, and produced artifacts. In each step, you can do any of the following:

  • Edit code - you can edit the code by editing the text directly.
  • Re-run the step - if a step failed or produced unsatisfactory output, you can re-run it without affecting other steps.
  • Provide feedback - you can give natural-language feedback describing any desired change to the code; the system regenerates the code for that step based on your input, and you can re-run it - without affecting other steps in the workflow.
  • Re-execute Step - you can re-execute a step to refresh its output or apply changes.

After re-running steps, click Update Status to refresh the summary. Click Proceed to continue to result analysis and manuscript drafting.

Post-hoc step revisitation

At any point after execution you may return to an individual step and supply natural-language feedback describing the desired modification - a methodological refinement, a parameter adjustment, an alternative model specification, or a corrected interpretation. You may then choose to propagate the revised outputs into the manuscript, at which point the Reporting Agent selectively regenerates only the sections whose input has changed - preserving editorial continuity while keeping the final document faithful to the most recent analytical state.

Returning to a Task Breakdown card:  Proceed and Provide feedback on a Task Breakdown card always resume that card's own turn, in Research and Spatial Analysis alike, never an earlier or later turn of the conversation. A card works only while its turn is still waiting. Once a newer request in the conversation has replaced it, clicking it shows "This Task Breakdown is no longer waiting". Send your request again to continue.

The manuscript deliverable

The reporting pipeline produces a structured research paper with standard academic sections:

  • Title and Abstract - including structured Background / Methods / Results / Conclusions and keywords.
  • Introduction - framed with literature and study objectives, including the gap in prior work that the study addresses.
  • Methods - data sources, study area, and analytical methods, following the approved research plan.
  • Results - quantitative findings, written from the actual step outputs, with the figures and tables from the catalog.
  • Discussion and Conclusion - interpretation, comparison with prior studies, significance, and implications.
  • References - compiled from the papers cited in the text.

Before drafting, the Reporting Agent searches Semantic Scholar using your question and the objective titles, and sorts the papers it finds into foundational, methodological, regional, and gap-evidence studies. The Introduction and Discussion cite from this set. Figures and tables are renumbered in the order they appear in the text.

If one section fails to generate, a placeholder is inserted and the remaining sections are still written. You can regenerate the failed section later.

The finished manuscript can be downloaded as Markdown, Word (.docx), or PDF. Individual stages - analysis, manuscript, specific steps - can be re-run or refined without starting over. When you re-run the manuscript after changing steps, only the sections whose inputs changed are rewritten: changes to the plan update the Title & Abstract, Introduction, and Methodology, and changes to execution results update the Title & Abstract, Results, Discussion, and Conclusion.

Chat Mode

Chat: Plain conversational QandA - no workflow is launched.

Use Chat mode to ask questions, clarify concepts, or plan your approach before committing to an analysis. For example:

  • "What's the difference between Global and Local Moran's I?"
  • "Which data source should I use for county-level income?"
  • "How should I frame a study of air quality and rurality?"

Chat mode answers directly without generating or running code.
